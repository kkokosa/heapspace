# Heapscape reference

[Quick start and daily use](../README.md)

All commands below run from the repository root, not the `docs` directory.

- **Heapscape** is a local, browser-based .NET dump explorer using Three.js and Microsoft ClrMD.
- run on Windows x64 with PowerShell 7, the .NET 10 SDK, Node.js 22.12+ (or a newer supported Node release), and a WebGL2-capable browser:
  ```powershell
  git clone https://github.com/kkokosa/heapspace.git
  Set-Location .\heapspace
  pwsh -File .\Start.ps1
  ```
  - open http://127.0.0.1:5077; the server deliberately binds to loopback, not the network.
  - use `pwsh -File .\Start.ps1 -Port 5087` for an alternate loopback port, or `-Port 0` for an OS-assigned port printed at startup. Direct DLL launches accept `--Heapscape:Port=5087`; start the DLL with `Server` as the working directory so static assets resolve correctly.
  - `Start.ps1` checks JavaScript dependencies and restores the locked versions when missing or mismatched, then builds the frontend and starts ASP.NET. Stop with Ctrl+C.
  - both PowerShell launchers use the normal configured NuGet sources (normally the official v3 feed). Override explicitly with `-NuGetSource https://api.nuget.org/v3/index.json`, or use `-NuGetSource https://www.nuget.org/api/v2/` if v3 is unavailable. Restore failures are reported; neither launcher silently falls back, disables TLS checks, or changes machine-wide settings.
  - frontend assets are bundled locally. No CDN, cloud upload, telemetry, or symbol-server requests are used by the viewer.
  - analyze trusted dumps only. ClrMD loads native DAC code; a worker process provides crash containment and cancellation, **not a security sandbox**. Do not expose this server to the internet.
- explore:
  - `Open a memory dump` opens a dialog containing the file picker, `Include strings`, processed dumps, and operation status/cancellation. Opening a new file does not delete an earlier processed dump. The dialog closes after successful loading; Escape closes it without changing selection or entering flight.
  - Explore and the top GC panel contain controls only. Detailed coverage, limitations, and status explanations live under the inspector's collapsed `Analysis notes`. The bottom-right foldable `Legends` panel contains only Prism memory materials and is hidden for themes without those materials.
  - top-level `Color by` offers object type or `Reachability type (root types)`, alongside generation/size modes. Root colors propagate all observed retaining-source categories; multiple categories produce striped faces. Stripes retain Prism surface patterns and array transparency, including during selection.
  - object hover adds a root-types line below the type, size, and address, using the same generation-scoped categories as reachability coloring and the inspector. Partial graphs explicitly identify observed, potentially incomplete provenance; a missing path is not automatically proof of unreachability.
  - `Highlight objects` chooses reachable, unreachable, or unknown for Gen 0/1/2, defaulting to Gen 0. Matching objects stay at full intensity and nonmatches become faint context, preserving the chosen colors and textures. Matches are prioritized within the object budget and sampled across the matching heap regions rather than taking the first matching address range; the status reports how many are actually displayed. No reference-depth expansion is applied to this analysis focus.
  - collection scope and the reachability-choice dropdown appear underneath `Highlight objects` only while it is enabled. Normal browsing uses full-graph root provenance for coloring, hover, and `Reachable by`, rather than an invisible previously selected generation scope.
  - captured/walked coverage and partial/unverified warnings are available in `Analysis notes`. Dropdown counts describe captured objects, not the whole process. For incomplete evidence, `Unreachable (unavailable)` leaves the overview visible; it is not an empty proven-dead set. Choose `Unknown` to highlight objects without recovered retention paths, which may be live or dead.
  - in a complete verified full-GC graph, reachable and unreachable partition the collectible managed objects, including SOH/LOH/POH. Frozen/permanent objects remain outside collection. A partial graph also has an unknown set, and sampled-out objects are absent from all displayed sets. `Gen 2 / full` changes the condemned generations, not capture completeness.
  - schema-5 analysis captures every walkable managed object, field/array/dependent reference, root, finalization registration/slot, and valid free range. There are no object/reference/root sampling caps. Rendering budgets affect only the scene, never the analysis graph. Older sampled snapshots require reanalysis; increasing their rendering budget cannot recover omitted paths.
  - complete graphs are loaded incrementally from the response byte stream, without a heap-sized JSON text buffer or the JavaScript single-string size limit. Repeated type/label strings and reference IDs share storage. Large heaps still need sufficient memory for their complete graph, indexes, reachability and layout; worker failures are explicit rather than silently returning a sample.
  - changing the highlight choice clears an existing object/root/card/search selection. Selecting an object or site afterward temporarily takes focus; changing the choice reapplies the full matching set. `X` clears both selection and analysis focus. Finalization is included among reachable retention sources, older generations are outside the collection, and incomplete evidence stays unknown rather than becoming an unreachable match.
  - the object inspector pairs address/bytes and generation/segment into two rows. `Reachable by` lists recovered retaining-source categories, or displays `Not reachable` only when the complete graph proves it; missing paths in partial captures remain `Unknown`. Available content previews and exact incoming/outgoing slot references remain, without rendering diagnostics or per-generation collection predictions.
  - Gen 0/1 analysis includes references from uncondemned older objects, so a root-unreachable young object may still survive an ephemeral collection. LOH/POH count as Gen 2; frozen allocations are permanent. Weak handles and named-field annotations do not seed marking; dependent edges activate only after their primary is marked.
  - absence of a root path is classified as unknown for sampled/capped graphs, unresolved retaining endpoints, unknown generations, failed heap verification, or incomplete finalization metadata. Older snapshots require reanalysis for negative classifications. A candidate is not a guarantee about the next live GC: mutation, resurrection, finalizer suppression and concurrent collection are not simulated.
  - finalizable-object registrations come from `ClrHeap.EnumerateFinalizableObjects`; the ready queue remains a separate retaining root source. Registrations and all objects reachable from them are conservatively protected, including cases where finalizer-suppression state was not decoded.
  - schema-4 and newer analyses include actual finalization-queue storage, pointer slots, ready-entry classification and decoded card states. Schema 5 removes the finalization-slot capture cap. Card visualization metadata remains independently bounded at one million cells; this does not truncate the object graph or determine reachability. Unsupported/unreadable card data is explicit.
  - each heap's finalization storage is split into separate `Finalizer queue` and `fReachable queue` cubes using ClrMD's reported ranges. `FinalizerQueueObjects` covers the full used slot range; `FinalizerQueueRoots` identifies the ready-for-finalization subrange. The remaining range contains registrations not yet ready. These are sections of shared native storage, not invented independent allocations.
  - queue sizes, slot positions and reference origins use each section's exact byte bounds. Registered sections are yellow; fReachable sections and their outgoing references are orange. Ready roots are deduplicated; registration links remain explicitly conservative. Queue boxes can be selected directly or reached from a root's `Inspect queue section`; `Frame queue sections` frames both sections.
  - empty queue sections have a labeled zero-byte wireframe marker instead of a fabricated memory volume or dummy root. In the fixture snapshots, console has 27 registered slots and 14 fReachable slots; ASP.NET and Orchard have empty fReachable ranges. Existing saved metadata contains the needed boundaries, so the display split does not require reanalysis.
  - card tables are always displayed as rectangular grids over applicable captured regions. Amber cells are observed dirty bits, dark cells are observed clean bits, and gray/unavailable maps are not decoded. A dirty-cell selection highlights captured older source objects overlapping that cell, including straddling objects and objects without a captured young target, plus young descendants reached through dirty old-to-young slots. These are scan candidates, not a trace of exactly what a live GC scanned.
  - each decoded table has an in-world `Scan Gen N` toggle next to its rectangle. It highlights source scan candidates across all captured dirty cells and their captured young descendants. Multiple tables can be enabled together; shared descendants are deduplicated. Toggles remain pickable while unrelated card sheets fade, and toggling the last table off clears focus. The inspector separates source/descendant counts and displayed coverage; display budgets still apply.
  - card inspection reports its scan scope: Gen 0 during normal browsing, or the active collection scope while highlighting. Only uncondemned older source objects contribute. Full GC has no ordinary older generation for this card-based attribution; dirty cards are bookkeeping, not independent roots or exclusive retention causes.
  - focused views dim card sheets and unrelated finalization areas to the fixed 5% context opacity. The selected card's own sheet stays emphasized. Dimmed sheets/queues do not intercept ordinary object picking; clear focus to pick another card.
  - click `Explore the heap.` to fold or reopen the control panel; the heading remains accessible while scrolling.
  - upload a full `.dmp` or ELF `.core` file, up to 2 GiB. Filename filtering in the picker can be changed to all files for extensionless Linux dumps.
  - left-drag orbits; right-drag pans without clearing the selection; the wheel zooms. Click a box to inspect. `F` toggles flight and `G` focuses. `X`, the clear-selection button, clicking the selected item again, or an empty-space left-click clears selection. Right-click never deselects.
  - outside flight, `W`/`S` pan up/down and `A`/`D` pan left/right in the camera plane; `Q`/`E` rotate around the orbit target without changing its distance. Panning speed follows zoom distance. Text inputs, dropdown typing and modified browser shortcuts are not intercepted; the dump dialog keeps its own keyboard events.
  - `F` also works while a panel checkbox, dropdown, slider, or button has keyboard focus. It enters flight without clicking the viewport, preserving GC highlighting and object selection. Text-entry fields such as object search keep normal typing; browser shortcuts such as Ctrl+F are not intercepted.
  - in flight, `W`/`S` move along the viewing direction, including pitch. `A`/`D` strafe and `Q`/`E` adjust altitude. Press Space to toggle normal/slow flight (one tenth speed); releasing it does not change the mode and key repeats do not toggle again. Hold Shift for fourfold speed, overriding either mode; release Shift to return to the chosen normal/slow mode.
  - the flight hint shows Normal, Slow, or Fast. The normal/slow choice persists until Space is pressed again, including leaving/reentering flight; a fresh page starts in normal mode. Neither modifier changes the base/wheel speed, and diagonal movement remains normalized. Space outside flight keeps its usual UI behavior.
  - Ctrl is no longer the slow modifier: browsers may handle Ctrl+W and close the tab before the page can prevent it. Toggle slow flight with Space and hold `R` while clicking to pick roots/slots during movement. Ctrl-click remains available when not combined with browser shortcuts.
  - flight hover continuously inspects the central crosshair, including while moving without mouse events. `X` clears selection without leaving flight or stopping held movement keys; right-click preserves it. Escape exits pointer lock and also clears selection.
  - `Prism` is the default theme, with semantic crystal materials and reference bloom. `Atlas` preserves the original look, `Matrix` adds green phosphor/wireframes, and `Neon Circuit` adds cyan/magenta circuits. Switching themes does not change addresses, sizes, node positions, or graph semantics.
  - Prism patterns distinguish strings (diagonal bands), arrays (cell grids), generic objects (granular crystal), known built-in scalar/value types (data dashes), and unknown types (contours). Native/unmanaged mappings are plain amber, without a material pattern. The memory-material legend identifies these categories; custom value types are not guessed from names.
  - Prism pattern variation uses captured type, byte size, and outgoing-reference metadata. Available previews contribute only when previews were enabled during analysis; otherwise only metadata is used. Previews may be truncated. Decorative surface cells are not a raw-byte or array-element map; exact reference-slot markers remain the address-grounded representation.
  - Prism object illumination stays on faces, inner rims, edges and corners, without contributing to external bloom. Its always-enabled reference-only bloom pass adds halos to streams, routing collars and signals; opaque objects and opaque-array depth passes still occlude that glow. Labels and selection render separately; choose another theme for a non-bloom presentation.
  - reference signals always animate at `Very fast` (the existing 3x speed setting), with no speed control. Atlas uses three packets per sampled path, Matrix six, Neon Circuit five, and Prism four. Prism uses golden pulses with warm-white heads and tapered amber tails inside cool streams. These illustrate a static graph, not measured live traffic. The simplified viewer intentionally keeps animation enabled regardless of reduced-motion preference; no CDN or model service is used.
  - Prism samples at most one animated source/target route per shared directed region-pair/reference-kind trunk, avoiding dozens of overlapping trains that would look like a solid gold beam. Direct/local routes can still animate independently. Every animated route is a real captured reference; this sampling does not remove rendered references.
  - golden tails follow arc-length positions, shorten naturally at the source, and never wrap into a false line from target back to source. Their approximate screen-length stays bounded as the camera approaches.
  - region wireframes and labels never intercept hover or clicks. There is no global `Jump to region` selector. The segment value in an object's compact facts is a contextual link to that region; queue roots and card inspectors retain their relevant contextual navigation.
  - physical GC region/segment grouping is always enabled. Actual regions/segments are grouped into GC-heap containers and labeled with two lines: `Region 29/Gen 0`, then `Heap 2/0x...`. Region numbers follow address order within the dump. Runtime identifiers are omitted from these display labels but retained in internal identities and grouping.
  - several physical units can have the same generation label. Conversely, a classic ephemeral segment may contain several logical generations and remains one physical unit. The inspector shows captured generation membership alongside ClrMD's generation, committed, and reserved address ranges; no region sizes or boundaries are guessed.
  - physical grouping adds GC-heap containers; a region's inspector can inspect its owning heap and that heap's individual regions. Containers are visual groups, not additional allocations or contiguous virtual-address intervals. This represents CLR allocator organization in virtual memory, not physical RAM pages.
  - physical grouping affects unit placement, not object sizes, segment-relative placement, real gap volumes, slot addresses, or graph edges. The renderer retains its internal alternative arrangement for regression checks, but the simplified viewer consistently uses physical grouping without a toggle.
  - region labels retain readable 110-230-pixel size bounds but fade smoothly with absolute distance and relative depth among visible labels. Nearby labels are clearer; distant ones recede. The selected region remains emphasized, overlapping labels are suppressed, and plaques never write depth or intercept picking.
  - region floor labels are always on: borderless region/generation/heap text and the actual address-span size at the front and back of each managed region's base. Labels remain horizontal, respect solid-object occlusion, recede with distance, and never intercept picking. Their facing and baseline adapt when viewed from below or the opposite side, keeping glyphs readable.
  - region dimension arrows and their control are removed. Floor labels retain the actual address-span size; neither hypothetical cube-byte values nor axis-name labels are drawn.
  - within a managed region, increasing addresses are packed along positive X, then into successive positive-Z rows, then positive-Y layers; X resets at each new row and X/Z reset at a new layer. A higher object-center Y alone does not imply a higher address because box heights vary. Region/heap grouping introduces further local coordinate resets.
  - these are address-ordered shelves, not a linear virtual-address coordinate system. Real gap volumes, variable object sizes, gutters and outer padding prevent assigning bytes-per-edge to a region frame. Object volume still uses the shared scale of 32 bytes per cubic scene unit; exact byte ranges remain in the inspector. Native/root slot projections use their separate address-folding schemes.
  - SOH, LOH, POH, and frozen heaps are always included; object type coloring is the default. Each type gets a deterministic shade from the selected theme's palette. Generation and logarithmic-size coloring remain available, region outlines retain generation colors, and hover/inspection identifies root-source categories without adding color legends.
  - intra-region address gaps reserve byte-proportional volumes instead of being packed away. Their outlines are always enabled: confirmed GC free ranges use solid neutral gray and other uncovered spans use darker dashed gray, distinct from generation colors. A region's inspector lists its largest gaps with exact addresses, bytes, and classification.
  - `Find object(s)` is a separate panel below Explore, folded by default. Search the full captured graph by type, hexadecimal address, or available preview; rendering limits do not restrict search.
  - the list previews up to 40 matches, while `Select all results` selects every matching captured object. The inspector reports the total and can frame the group; reference depth expands their combined neighborhood. Search selection raises the object budget to All captured when needed to include every match. Subsequent display-limit changes remain reflected in the rendered-selection count.
  - analysis warnings and interpretation details remain under the inspector's collapsed `Analysis notes`; the old floating coverage panel is removed.
  - inspect incoming/outgoing field references, named statics, thread statics, stack slots, handles, pinning, conditional dependencies, and ready-for-finalization roots.
  - `Find one retaining path` performs an on-demand reverse search through the indexed captured graph. `Show all retaining routes` performs a full root-to-object subgraph query, including all captured retaining sources that can reach the target and excluding unrooted predecessor branches. Shared branches and cycles are merged into one finite graph rather than enumerating infinitely many cyclic walks.
  - route queries exclude weak/dependent handles as independent seeds and exclude field annotations. They include finalization registrations conservatively and permanent frozen sources without fabricating slot addresses. Partial graphs may omit routes; display budgets can limit the shown portion of the complete query result. These are not retained-size calculations or guarantees about a future collection.
  - stack regions have labeled rectangular frames and individually positioned root markers. Select stack boxes for managed frames and associated roots.
  - handle markers live at their reported source-slot addresses, rather than in an artificial row. Native root-address buckets are part of the same address-sorted atlas; the inspector preserves exact addresses and explains projected or unavailable positions.
  - root and array-reference starts are smooth shaded beads instead of unlit diamond/tick glyphs. Root beads retain strong/weak theme colors; array slots use the reference color. Marker sizes are semantic glyph sizes, not additional memory allocations.
  - Ctrl-click, or holding `R` while clicking, targets a root or array slot through its container. Both modifiers also switch hover to sites; `R` is recommended in flight because it does not form reserved browser shortcuts with movement keys. Ordinary object picking is unchanged.
  - single-site selection highlights only that root/slot connection and marks it with a camera-facing ring. Other sites remain faint context where available. Ctrl-click the same site again or press `X` to clear it; right-drag remains available for panning. `Inspect target` expands its object neighborhood.
  - the inspector reports exact source addresses and retains the distinction between a GC root, a field annotation, and an ordinary array reference. A single slot is not automatically claimed to be a retaining root. Unknown/uncaptured targets remain explicit instead of receiving fabricated edges.
  - inspector root lists select the same individual sites. Ctrl-clicking an array-reference row selects its source slot; a normal click still follows its target.
  - select native blocks for virtual addresses, protection/state metadata, and overlaps with managed segments, stacks, modules, and CLR-native loader/JIT/handle heaps.
  - approach an array to fade its shell and reveal the reference slots inside it. Outgoing array references display their exact source-slot address in the inspector; small internal markers identify rendered slots, including the `System.Object[]` arrays used by pinned/static roots.
  - references follow curved, shared corridors between regions. Each directed region-pair/reference-kind bundle has exactly one central trunk; counted source branches join its inlet and counted target branches leave its outlet. Individual paths are not drawn again through the trunk. Moving particles indicate source-to-target direction, not actual runtime activity.
  - selection and analysis focus add shaded directional cones near both endpoints of every drawn highlighted reference, including roots and internal array slots. The source cone points away from its source, and the target cone points toward its target along the actual curve. Their radii track pipe width so small-object arrows do not disappear inside the pipes. The overview has no cones; reference budgets still determine which links are drawn.
  - cones originating inside arrays, including roots stored in array slots, use the pointer-cell size rather than the entire array's dimensions. They are at most one quarter of the ordinary source-cone length and do not inherit the pipe's minimum radius. Target cones and ordinary object arrows retain their existing size and direction.
  - inter-region bundles choose the nearest pair among six face-center ports per region (positive/negative x, y, and z), rather than forcing every link above the top. Junctions sit just outside the selected faces; cubic trunks align with outward face normals and join branches smoothly. Small collars mark used routing ports, not GC roots or allocations.
  - connection width is fixed at the established 1.5x presentation multiplier. Shaded pipes and wide lines retain nominal relative bundle thickness without changing endpoint positions or reference counts.
  - object references, roots/handles, finalization queue areas, native memory, and card tables are always enabled. Inter-region layout is always bundled streams; same-region arcs remain local. Detailed reference coverage stays in `Analysis notes`.
  - object-budget choices show the maximum percentage of successfully walked heap objects they can cover. The actual rendered count reports percentages of both walked objects and the captured graph, accounting for filters, sampling, selection, and context opacity. Faint context counts; context at zero opacity does not. These are scene-membership counts, not camera-frustum/pixel visibility counts.
  - choose `All captured (100%)` in `Visible object budget` to remove the object display cap. Choose `All eligible (100%)` in `Reference budget` to remove the object-reference, root-link, and root-marker display caps. Existing smaller defaults remain available.
  - full display does not repeat analysis or recover omitted heap objects. For the broadest available graph, choose both full options and clear selection. References with uncaptured endpoints cannot be drawn; actual captured/eligible percentages remain available instead of claiming whole-heap completeness.
  - reference coverage shows drawn/captured percentages and the percentage of references eligible in the current view. Object visibility, selected depth, default display limits, and analysis caps can omit links. If analysis sampled objects, capped edges, or encountered invalid objects, the total heap reference count is explicitly unknown. Root/handle-link percentages use their own captured-record denominator.
  - connections inside the same region always use short paths between facing object surfaces or internal array slots, even in bundled mode. Their control points stay inside the region instead of leaving it to visit an overhead trunk. Inter-region connections still bundle normally.
  - selected-neighborhood emphasis is always enabled: unrelated displayed objects, stacks, roots, native blocks, card sheets, and finalization areas remain non-pickable at a fixed 5% opacity. GC analysis focus uses the same visual language. Escape deselects outside the dump dialog; inside it, Escape only closes the dialog.
  - object/group inspectors have separate `Incoming depth` and `Outgoing depth` inputs, each from zero to five hops. Each direction is traversed independently from the selected seed objects, rather than switching direction at intermediate nodes. Their union is displayed with actual edge directions. Changing depth exits all-routes mode; `Frame reference neighborhood` fits the highlighted graph. Region inspection uses the compact segment-field link instead of extra object action buttons or a global selector.
  - reserved native address space is excluded by default. Enable `Include reserved address space` to include it at its true proportional volume; the sample dumps contain multi-terabyte reservations that dwarf committed memory.
  - previously uploaded dumps can be reopened or removed after a browser refresh. Only one upload/analysis runs at a time, but completed dumps do not occupy analysis slots and have no arbitrary count limit. They consume local disk space until removed or the server shuts down; remove old uploads when no longer needed.
- interpretation and limits:
  - card tables are bookkeeping, not independent roots. A dirty bit identifies source memory to scan, not a guarantee every covered object is live or that a younger target has only one retention cause. The general reachability model remains conservative over old-to-young graph edges; card selection adds evidence from actually observed dirty bits.
  - the decoder is verified for Windows x64 CoreCLR 10.0: each card bit covers 256 source bytes and each little-endian 32-bit word covers 32 cards. The word address is the ClrMD indexing base plus four times the global card-word index. Other runtime/architecture combinations are reported unsupported rather than guessed. Card sheets are address projections, not views of physical RAM or additional allocations.
  - lower-level DAC `DacpGcHeapDetails.card_table` is obtained through `ISOSDacInterface.GetGCHeapDetails` (server GC) or `GetGCHeapStaticData` (workstation GC). A debugger or ClrMD data reader can inspect the underlying memory with the correct runtime-specific layout. Ordinary heap graphs and GC event traces do not themselves supply decoded dirty-card contents.
  - addresses remain hexadecimal strings through JSON and JavaScript, preserving all 64 bits.
  - segment bounds, generations, committed/reserved ranges, object sizes, and reference edges come from ClrMD. Object, stack-extent, and native-fragment box volumes are proportional to bytes on one shared scale: 32 bytes per cubic scene unit, with a 0.9-unit minimum side and no maximum size cap. An allocation eight times larger has twice the side length. Selection adds an outline, never inflates a box.
  - regions, stacks, and native fragments are sorted by exact virtual address and packed into 3D shelves. Gaps between separate regions remain condensed. Within each region, leading/inter-object/trailing address spans are preserved as gap volumes in the same address-ordered packing as objects.
  - each gap volume uses the same bytes-to-volume scale as object boxes, without the tiny-object minimum-size cap. Only ClrMD `IsFree` ranges are confirmed GC free space. Other spans may contain omitted objects, alignment, allocation contexts, or unwalkable memory and are never assumed free.
  - visual gutters, shelf slack, and outer region padding remain additional to the measured gap volumes. The layout preserves byte coverage and free-space volume, not a linear address-distance metric in 3D. Filters and object budgets do not repack these intervals.
  - up to 5,000 largest gap outlines are drawn, while every gap still participates in packing. Root addresses inside unrepresented ranges use their corresponding gap volume rather than an unrelated point in the region. Overlapping/out-of-region object and free spans are rejected explicitly.
  - schema-2 and newer analyses include free-block ranges; schema 5 removes the former 250,000-range cap. Older snapshots still preserve address gaps but may mark them unclassified or limited; updated analysis identifies every valid free block.
  - native mappings are split around managed object-range, stack, and root-address extents so those addresses are not drawn a second time as native boxes. Native root regions are 4 KiB address buckets clipped to known mapping boundaries, not inferred handle-table allocation boundaries. An address outside captured mappings remains explicitly marked as unmapped. Region wireframes are packing guides, not allocations with proportional volume.
  - root positions within native or stack regions use a quantized 16-by-16-by-16 address lattice. Slots inside captured managed arrays use the same internal pointer-cell mapping as their outgoing references; other managed-object slots project onto the object's top face. `StaticVar`/`ThreadStaticVar` records can identify CLR storage-object anchors instead of true handle slots; the inspector distinguishes these. A root with no usable address is explicitly associated with its thread or placed in an `Unlocated roots` marker, never assigned an invented address.
  - ClrMD reference offsets exclude the method-table pointer: an array source slot is the object address plus the target pointer size plus the reported reference offset. Addresses retain full 64-bit precision. Pointer-sized cells, including header offsets, are folded across x/z/y inside the array cube; this is an address-grounded visualization, not a claim that physical arrays are three-dimensional. Different slots keep separate bundle inlets. Dependent handles are logical edges and do not get fabricated element addresses.
  - transparent boxes, labels, guides, tubes, and signal sprites do not write depth; glass draws before connections. Opaque objects still occlude geometry normally. Approaching an array smoothly fades its surface toward 18% opacity, using a per-instance alpha and an opaque-only depth prepass so only fully opaque far arrays mask interior geometry.
  - unavailable/invalid array offsets or unknown pointer widths are reported in reference coverage rather than converted into guessed slot addresses. Existing uploaded snapshots already contain the offsets needed for supported architectures; no re-upload is required for this renderer update.
  - display-budget, color, and selection changes do not move boxes. Toggling reserved-address inclusion or physical GC organization deliberately recomputes the address atlas. Root markers and GC-heap container frames are semantic guides rather than additional memory allocations.
  - generation labels reflect the dump, not an inference from object size. A pinned SOH handle does not turn that object into a POH allocation.
  - weak handles do not retain objects. A dependent-handle edge retains its secondary only when its primary is live. Finalizer roots are the ready queue, not every object with a finalizer.
  - ClrMD 4.1.745802's authoritative root enumeration includes runtime-specific static-storage roots and async-pinned children. Static/thread-static field names are additional best-effort annotations, not independent retaining roots: collectible type lifetimes can be conditional. Generic, value-type, or unavailable metadata may prevent a name from being recovered.
  - every valid object is captured and verified while walking its segment, and all enumerated references and roots are retained. Corrupt/unwalkable memory is reported and prevents unsafe negative reachability conclusions. Stack previews remain capped at 64 frames per thread, card sheets at one million cells, and workers at ten minutes; a worker timeout fails the analysis rather than publishing a truncated graph.
  - default display limits are the selected object budget, 6,000 object edges, 4,000 root links, and 10,000 root-address markers. Full options remove those corresponding limits; native fragments remain capped at 5,000. A limited overview reserves up to 40% of its object budget for complete reference pairs, then samples across the heap.
  - default focused exploration is bounded at 2,000 objects, 6,000 edges, and 100,000 scans per phase. Full-object mode removes the neighborhood node cap; full-reference mode removes the neighborhood edge cap. Either full mode removes the scan cap. Selected depth and explicit filters remain intentional scope limits.
  - up to 240 trunks and 500 focused branches/direct arcs use tube geometry; remaining pieces use screen-space wide lines instead of single-pixel lines. The width control multiplies nominal radii and line widths. Before that multiplier, bundle area scales with reference count up to a 0.7-unit radius cap. Thickness does not represent retained bytes, distinct paths, or traffic.
  - dense full graphs can consume substantial browser/GPU memory and pause the UI while rebuilding. Large instance batches are partitioned by region for picking, and line geometry uses typed chunks rather than nested arrays. Lines use 24 segments normally, 8 above 20,000 displayed links, and 4 above 100,000; this reduces geometric detail, not the number of eligible references represented.
  - packets and trails animate up to 96 actual source/target reference paths. For a bundled reference the signal traverses its correct source branch, shared trunk, and target branch, not an arbitrary combination of bundle endpoints. More packets in a theme do not mean more references or measured traffic.
  - port selection minimizes face-center distance among 36 combinations; it does not solve global obstacle avoidance. Routes are schematic wiring, not physical pointer trajectories. A bundled many-to-many view does not imply every source connects to every target; exact pairs remain in the inspector.
  - large-dump root enumeration can take several minutes. Analysis stays in a cancellable worker and the page reports its status.
  - absence of a visual edge or root is not proof of absence from the process. Corrupt/incomplete dumps, analysis caps, and unavailable DAC data can leave unresolved endpoints.
  - native views show Windows MemoryInfoList mappings, captured-range fallbacks, or little-endian ELF64 PT_LOAD segments. Overlap labels are not exclusive ownership. They are not malloc block boundaries; arbitrary native pointers and native-only thread roots are not guessed.
  - matching local runtime/DAC, OS, and analyzer architecture are required. Windows x64 is exercised by the fixtures. Cross-OS/cross-architecture analysis is not supported or verified; Linux ELF mapping parsing is present but not end-to-end validated here.
  - previews are opt-in and limited to strings (160 characters) and array lengths. Arbitrary object methods are never invoked; arbitrary nested value inspection is not implemented.
  - dumps and graphs live under the OS temp `Heapscape` directory. Clear deletes their files; graceful shutdown cleans the session directory. Forced termination can leave files for manual removal. Deletion is not secure erasure.
